CI gate definitions. The actual CI runner/workflow engine is wired up in task 0.D (qa): `.github/workflows/ci.yml` — Fast gate (v1-untouched, format/lint/typecheck, unit tests, OpenAPI schema build, migration-file syntax) and Full gate (the full `tests/` suite, currently unit+integration; contract/state/security/e2e/performance grow as Phase 1+ adds tests to those suites, per `tests/README.md`), per `docs/reports/PLAN-MISSION-1.md` §2. Migration rehearsal (empty + seeded DB, idempotent repeat, FR-PLT-12), the invariant-quarantine test (FR-PLT-13, P007), and the worker-restart-resume test (FR-JOB-03) are covered by existing tests under `tests/integration/` (`test_migrations_runner.py`, `test_invariant_quarantine.py`, `test_jobs_store.py`) and run as part of the Full gate above — no separate CI step is needed for them.

## Security gate — stub plan (0.C)

`NFR-SEC-07` (dependency/secret/license scanning) and `NFR-SEC-09` (image digest integrity) require CI checks that are not wired yet — no CI runner exists until 0.D. This section is the plan those checks are wired against; it names candidate tool categories, not locked-in tool choices (no new dev dependency has been added for this yet — that is a 0.D decision, made when the check is actually wired, same discipline as the migration-runner-tool choice in `migrations/README.md`).

| Check | Purpose | Candidate approach | When it blocks |
|---|---|---|---|
| Secret scan | Catch a committed credential/token before it reaches history | A git-history-aware scanner (e.g. gitleaks/trufflehog-class tool) run on the diff for every PR | Fast gate, every commit, once wired in 0.D |
| Dependency scan (SCA) | Catch a known-vulnerable pinned dependency (`pyproject.toml` pins every version already — §"Commands" in `CLAUDE.md` — so a scan has a fixed target to check) | A Python-ecosystem SCA tool (e.g. pip-audit/osv-scanner-class tool) against the resolved dependency set | Phase 6 task 6.B — now wired: `ci.yml`'s `security-scan` job (`needs: fast`, does not need the DB), tool choice `pip-audit==2.10.1` (`pyproject.toml`'s `dev` extra). **Non-blocking / informational** for now — real findings exist against this repo's current pinned versions (`pip`, `pytest`, `starlette`; confirmed by a local run, 2026-08-16) with no established clean baseline yet, so the step cannot fail the job (`continue-on-error: true` + `\|\| true`), per this row's own already-recorded rollout plan ("Full gate initially ... promoted to a Fast-gate blocker once the baseline is clean"). JSON report uploaded as the `pip-audit-report` build artifact. Promotion to a blocking gate is a separate future task once the baseline is triaged clean. |
| License scan | Catch a dependency whose license is incompatible with distribution/use | A license-listing tool (e.g. pip-licenses-class tool) with an explicit allow-list of acceptable licenses | Phase 6 task 6.B — now wired: `ci.yml`'s `security-scan` job, tool choice `pip-licenses==5.5.5`. **Blocking from day one** (unlike the dependency-scan row above, a license violation is a real binary pass/fail with no "clean baseline" ambiguity) — `--allow-only` enumerates the MIT/BSD/Apache-2.0/ISC/MPL-2.0/PSF-class license strings this repo's actual resolved dev-dependency set uses (verified locally, 2026-08-16: the full allow-list check exits 0 against the current dependency set). `--ignore-packages` excludes `uniwatch-v2` (this project's own code, no PyPI license classifier, would otherwise show as `UNKNOWN`) and `chardet` (LGPL-2.1, pulled in only as a transitive dependency of the `cyclonedx-bom` SBOM tool itself — never imported by product code, never present in a production image since `apps/*/Dockerfile` install without the `dev` extra; would need reassessment if it ever became a direct/production dependency). Markdown report uploaded as the `license-report` build artifact. |
| SBOM | Produce a machine-readable bill of materials for the built environment | A pure-Python SBOM generator (`cyclonedx-bom`, chosen over a Go-binary tool like `syft` to stay pure-Python) | Phase 6 task 6.B — now wired: `ci.yml`'s `security-scan` job, tool choice `cyclonedx-bom==7.3.1` (CLI invoked as `cyclonedx-py environment`). One CycloneDX 1.6 JSON SBOM generated per run, uploaded as the `sbom` build artifact — informational, not a pass/fail gate. |
| Image digest integrity | A deployed artifact must match the exact commit that was reviewed (v1 RN-11/RN-12 failure mode: tag drift) | Immutable image digest recorded at build, checked at production authorization against the reviewing commit | Production-authorization gate (`INV-14`), Phase 6 — both halves now wired. **Build half** (task 6.A): `ci.yml`'s `build-images` job, `docs/operations/release-manifest.md`. **Check-at-authorization half** (task 6.B): `scripts/authorize_deployment.py` — reads the manifest, verifies its `commit_sha` matches the PR's real head commit, verifies the approver is a distinct identity from the initiator (`docs/adr/0005-authority-model.md`'s `FR-AUT-06`), checks DB schema compatibility, then writes an append-only `deployment_authorizations` record — the first mechanical enforcement of the distinct-approver rule anywhere in this repo (previously a manually-asserted `WORKLOG.md` note only). Building this surfaced and fixed a real bug in `build-images`' own `IMAGE_TAG`: on a `pull_request`-triggered run, bare `github.sha` is GitHub's ephemeral test-merge commit, which matches neither the PR's real head nor its eventual merge commit — a manifest built from it could never be matched against anything real afterward. Fixed to `github.event.pull_request.head.sha \|\| github.sha`. |

None of the above was implemented in this task (0.C) — this table was the plan `0.D` (and later Phase 6 task 6.A, for the image-digest row, and Phase 6 task 6.B, for the dependency-scan/license-scan/SBOM rows) wired against, per `docs/reports/PLAN-MISSION-1.md` §2 ("CI security-gate stub ... план"). Full inclusion criteria and tool selection are recorded here (not silently decided) the moment each check is actually wired.

Everything else in the Fast/Full gate table (`docs/reports/PLAN-MISSION-1.md` §2, 0.D) is not wired yet — this file is extended, not replaced, when 0.D starts.
