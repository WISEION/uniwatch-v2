## 1. Целевая архитектура: три подсистемы + ядро

Система — это один организм из трёх подсистем данных и одного ядра решений. То, что сейчас строится (Phase 0–1), — это **первая подсистема**. Остальные подключаются позже к той же шине фактов.

| Код | Подсистема | Что видит | Горизонт | Фазы |
|-----|-----------|-----------|----------|------|
| **DFE** | Demand Foresight Engine | будущий спрос: сигналы → прогноз тендера → BOQ | будущее | Phase 0–2 |
| **SCG** | Supply Capability Graph | предложение рынка: материалы, труд, техника, репутация | настоящее | Phase 3 |
| **EL** | Execution Ledger | факт исполнения: план vs факт, кэш, исходы | прошлое | Phase 4 |
| **MDC** | Match & Decision Core | BOQ ↔ SCG, светофор, Go/No-Go, Bid/No-Bid | точка встречи | Phase 3–4 |

Ключевая петля, ради которой всё строится: **DFE даёт SCG время** (за 6–12 мес узнать, что понадобится, и нарастить базу заранее), **SCG даёт DFE фильтр** (не подсвечивать тендеры, которые физически не закрыть), **EL калибрует обоих** (факт прошлого = точность будущего). Первые две подсистемы работают с *обещаниями*; EL — единственная, кто знает правду.

DFE, который строится сейчас, — фундамент всей петли. Если у него грязный или не-верифицируемый вход, врут все трое.

- **INV-03 (уже в PRD) · Идемпотентность и возобновляемость.** Черновик предлагал это как «INV-7» — дословно существующий `INV-03` (Cursor двигается только после атомарного commit, `FR-JOB-04..06`). Уже реализовано в 1.B — распространять на всё, что добавляется.
- **INV-07 (уже в PRD) · Решение ≠ рекомендация.** Черновик предлагал это как «INV-8» — дословно существующий `INV-07` (Score создаёт recommendation/candidate, не решение). Выход MDC — управленческое решение с условиями и дедлайном (`Conditional Bid`), а не «советую участвовать». Формат — в §7.
- **INV-15 · Факт = кортеж, а не значение.** Любой атом данных в любой подсистеме хранится как `{value, source_ref, observed_at, ttl, confidence}`. Цена без даты — не факт, наличие без источника — слух. Записи без `source_ref` в normalized-слой не проходят. (Расширяет `DM-03` — provenance на каждой версии — явным TTL/confidence на уровне атома, а не только версии ресурса.)
- **INV-16 · Исходник неудаляем.** raw-артефакт (HTML, PDF, фото, голосовое, Excel) хранится вечно и адресуется из каждого производного факта. Любой normalized-факт должен уметь «сходить назад» к байтам, из которых извлечён. (Тот же принцип, что `DM-02`/`INV-02` для raw snapshot — распространяется на невекторные типы вложений: фото, голос, Excel.)
- **INV-17 · Каждый факт имеет срок годности.** TTL по классу: наличие — дни, цена — недели, квалификация бригады/репутация — месяцы, распоряжение о финансировании — 12–24 мес. **Точные числа TTL по классу — не решены**, тот же режим, что `TBD-01` (freshness/SLO) в PRD: остаются `TBD-TIS-01` до отдельного review, не подставляются как факт. Просроченный факт не участвует в расчёте без ре-верификации.
- **INV-18 · Нулевой порог входа («салфетка»).** Ни один поставщик информации (снабженец, прораб, вендор) не обязан знать классификаторы, категории и таблицы. Вход — папка/чат/голосовое. Извлечение и нормализация — работа системы, не человека. Структура живёт внутри, снаружи — хаос.

## 4. Phase 1 — остаток (закрыть ворота)

Цель фазы: **DFE умеет надёжно и безопасно затягивать тендерные документы целиком и переживать любые сбои источника.** До закрытия 1.E никакой Phase 2.

### 4.1 · Задача 1.C — Egress Validator + SSRF suite
**Зависимость:** ничего не блокирует, но блокирует всё остальное (живой фетчинг стоит на ней — INV-10).

Реализовать `docs/architecture/egress-validator-contract.md`. Central egress resolver, через который проходит **весь** исходящий HTTP.

Обязательное поведение:
1. Резолв хоста в IP **до** соединения; коннект по резолвленному IP (защита от DNS-rebinding).
2. Блокировать приватные, loopback, link-local, CGNAT, метадата-адреса (`169.254.169.254`), IPv6-аналоги, `0.0.0.0/8`.
3. Только `http/https`. Схемы `file://`, `gopher://`, `ftp://` и пр. — отвергать.
4. **Ре-валидация после каждого redirect** — новый Location проходит все проверки заново. Лимит цепочки redirect.
5. Timeout, max response size, allowlist/denylist доменов из конфига.
6. Каждый отказ — типизированное событие (для 1.D), а не молчаливый `null`.

**P301:** запрос на `http://169.254.169.254/...` и на приватный IP — заблокирован, залогирован с причиной.
**P302:** redirect с публичного URL на приватный IP — заблокирован на шаге redirect, не на исходном.
**P303:** DNS-rebinding кейс (хост резолвится в публичный, при повторном резолве — в приватный) — соединение идёт по первому резолвленному IP, ре-резолв не открывает дыру.
**P304:** легитимный внешний тендерный портал фетчится успешно сквозь валидатор без ложной блокировки.

### 4.2 · Задача 1.D — Exception queue
**Зависимость:** 1.C (её отказы — первый потребитель очереди).

Единая очередь для всего, что не прошло happy-path: drift-формы (INT-02), egress-блокировки (1.C), просроченные факты без ре-верификации (INV-17), нераспознанные артефакты «салфеток» (INV-18, появятся в Phase 3).

Требования:
1. Запись = `{тип, источник, raw_ref, причина, first_seen, attempts, next_retry, статус}`.
2. Класс «retryable» (сеть, timeout) vs «needs-human» (новая форма контракта, нераспознанный документ).
3. Backoff по retry; needs-human выносится в отдельный обзорный поток.
4. Разбор needs-human, приводящий к правке empirical contract, **автоматически снимает** аналогичные записи из очереди.
5. Очередь не теряется при рестарте (INV-03).

**P305:** drift-форма из 1.A попадает в очередь как needs-human с ссылкой на raw, а не роняет пайплайн.
**P306:** временная сетевая ошибка — retryable, уходит в backoff, при восстановлении обрабатывается без дубля.
**P307:** правка контракта закрывает все однотипные needs-human записи одним действием.

### 4.3 · Задача 1.E — QA gate (ворота Phase 1)
**Зависимость:** 1.C, 1.D.

Regression suite `P001/P002/P006/P007` + новые `P301–P307` зелёные на **реальных** данных. Acceptance proofs — воспроизводимые артефакты (сохранённые ответы + ожидаемый normalized-выход), а не описания.

**Ворота Phase 1 закрыты, когда:** весь фетчинг идёт через валидатор (INV-10); любой сбой источника попадает в exception queue, а не в `null`; сбор возобновляется с checkpoint (INV-03); полный прогон regression зелёный на живом портале.

## 5. Phase 2 — BOQ depth + Forecast layer (достроить DFE)

Цель: DFE не только затягивает тендер, но и **предсказывает его до публикации** и **раскрывает BOQ до атомов**, готовых к матчингу.

### 5.1 · 2.A — Полная строка BOQ
Довести `boq_import` от «страница затянута» до атомарной строки, пригодной для матчинга и расчёта.

Модель строки: `{раздел, code, description, unit, qty, spec_extracted, rate?, amount?}`, плюс распознавание:
- скрытых требований в description (марка бетона B25/B30, класс арматуры, стандарт AZS/ГОСТ/EN, «или эквивалент»);
- `preliminaries`, `provisional sums`, `prime cost` — как отдельные типы, а не обычные строки (на них горит маржа);
- приведение единиц к каноническим; склейка синонимов номенклатуры.

**P308:** реальный BOQ раскладывается на строки; каждая имеет unit+qty; preliminaries/provisional помечены типом; извлечённые spec-требования привязаны к строке.

### 5.2 · 2.B — Signal ingestion (ранние сигналы)
Источники прогноза (по горизонтам): бюджеты/инвестпрограммы, распоряжения (president.az, e-qanun.az), пайплайны доноров (WB/ADB/EBRD/AIIB), тендеры на ТЭО/проектирование, годовые планы закупок и **изменения** в них, вакансии заказчиков, назначения.

Каждый сигнал — факт по INV-15, привязан к **объекту** (заказчик/регион/тип проекта), не висит сам по себе.

**P309:** сигнал из реального распоряжения нормализован, привязан к объекту, имеет source+date+ttl.

### 5.3 · 2.C — Forecast engine (композитные триггеры)
Граф объектов + накопленные сигналы с весами и TTL. Прогноз = **пересечение независимых сигналов по одному объекту**, не одиночный сигнал.

> **Числа ниже — иллюстрация формы модели (три уровня уверенности по числу сошедшихся сигналов),
> не откалиброванные пороги.** Это тот же режим, что `TBD-03` (ML minimum labels/uplift/calibration)
> в PRD: конкретные проценты и горизонты остаются `TBD-TIS-02` до backtest на реальной ретро-выборке
> (`P310` ниже) — не подставляются как факт до отдельного review.

- слабый (`TBD-TIS-02`, иллюстративно ≈30%, гор. 9–12 мес): строка в программе + упоминание в стратегии;
- средний (`TBD-TIS-02`, иллюстративно ≈60%, гор. 6–9 мес): + тендер на ТЭО выигран + движение по земле/ОВОС;
- сильный (`TBD-TIS-02`, иллюстративно ≈85%, гор. 2–4 мес): + вакансия PM + допзапись в плане закупок + RFI.

Затухание по TTL; оборванная цепочка → объект в «замороженные», не удаляется (размораживается при новом бюджете/смене руководства).

**P310:** на ретро-выборке из ≥30 уже опубликованных тендеров восстанавливаются цепочки назад (распоряжение→ТЭО→вакансия→публикация); модель даёт калиброванные горизонты по каждому заказчику (холодный старт закрыт историей, а не годом ожидания).

### 5.4 · 2.D — Карточка прогноза + доставка
Карточка при пороге (≥50%): объект, предмет, оценка бюджета (из первичного документа), окно публикации, **три вероятности** (выйдет вообще / в окно / коммерческая привлекательность), **цепочка улик** с датами и ссылками, **Next Best Action**.
Доставка: еженедельный дайджест (только изменения статуса) + срочный алерт (горизонт сжался / конкурент сделал ход). Алерт → задача в трекере с дедлайном.

**P311:** карточка собирается только при пороге, содержит проверяемую цепочку улик; дайджест отдаёт дельты, а не ленту.

## 6. Phase 3 — Supply Capability Graph + Matching (второй брат)

Цель: оцифровать предложение рынка и научиться сопоставлять его с BOQ.

> **Явное отклонение от исходного master-plan, зафиксировано владельцем 2026-08-04, не решено
> молча.** Исходный `UNIWatch-v2-master-development-plan-2026-07-28.md` относил ingestion **реальных**
> данных поставщиков к Phase 7, только после отдельного legal/privacy/security gate — Phase 3 там
> строго synthetic-only (`FR-VND-06`, `ADR-0004`). Этот документ переносит реальный ingestion
> предложения (фото/голос/ERP чужих папок реальных вендоров) в Phase 3. Владелец подтвердил: речь не
> о поиске новых поставщиков (Unico QSC — 20 лет на рынке, поставщики уже есть и известны), поэтому
> отдельный внешний legal-gate для *уже существующих, известных компании* поставщиков не требуется.
> Базовая гигиена данных (PII контактных лиц в голосовых/фото, retention, кто видит) остаётся —
> см. `docs/decisions/OPEN-QUESTIONS.md` — но не как блокирующий отдельный gate, а как обычная
> внутренняя практика. Synthetic-sandbox (`FR-VND-01..06`) остаётся отдельно как способ тестировать
> сам движок SCG до/параллельно реальному вводу, не заменяется этим решением.

### 6.1 · 3.A — Салфеточный ingestion предложения
Вход по INV-18: папка/чат/Drive/SharePoint/ERP-выгрузка/голосовое. Конвейер OCR + ASR + парсинг кривого Excel → атомы `кто → что → сколько → почём → где → до когда → откуда знаю`. Подключение к чужим папкам вендоров (pull без усилий с их стороны).

Три слоя возможностей: **материалы** (TTL дни–недели), **труд** (бригады, допуски, загрузка; TTL недели–месяцы), **техника** (парк, ставки, дислокация, окна; TTL недели).

**P312:** фото прайса и голосовое «арматура 12, 200т, до конца месяца» → нормализованные факты с source+date+ttl, исходники сохранены.

### 6.2 · 3.B — Репутационный слой (четвёртый слой SCG)
Не рейтинг, а факты исходов: держит ли цену после выигрыша, держит ли сроки, качество/сертификаты/рекламации, финансовая дисциплина, поведение под давлением (продал ли чужую бронь в дефицит). Источник — исходы проектов (из EL, Phase 4), рынок, суды/долги. TTL: обнуляется при смене владельца вендора.

**INV-19 (репутация):** репутация — **коэффициент доверия**, через который проходят все статусы наличия и все цены SCG. Reserved у ненадёжного ≈ Confirmed у надёжного.

**P313:** голосовое «с этими больше не работаем, кинули по срокам на объекте X» → репутационный факт, привязанный к вендору, влияет на его статус наличия.

### 6.3 · 3.C — Executable Availability
Наличие — не бинарно. Градация: **Reserved** (юридически закреплён объём+цена) → **Confirmed** (физически подтверждён, не закреплён) → **Reported** (заявлен вендором) → **Unknown**. Взвешивается репутацией (INV-19).

**P314:** одна и та же позиция от надёжного и ненадёжного вендора получает разный эффективный статус при одинаковых словах.

### 6.4 · 3.D — Matching BOQ ↔ SCG (перевёрнутая логика)
Сначала **исполнимость, потом цена**. Порядок матчинга:
1. Кто гарантированно поставит требуемый объём в нужное окно (по spec из 2.A)? Остальные — исключены из ценового сравнения.
2. Среди исполнимых — сравнение по **TCO** = `цена + логистика + финансирование + страхование + резерв_риска(репутация)`, а не по прайсу.

Светофор строки: 🟢 = 2+ источника, **из которых ≥1 с положительной историей исполнения**; 🟡 = один источник / цена старше TTL / наличие под вопросом; 🔴 = нет ни у кого / spec не закрывается.

**P315:** BOQ раскрашен; 🟢 требует подтверждённой истории, две цены от незнакомцев дают 🟡; выдаётся сводка «X% зелёного / Y% жёлтого / Z% красного по деньгам».

## 7. Phase 4 — Execution Ledger + Decision Core + Calibration (третий брат + ядро)

Цель: замкнуть петлю. Считать решение, ловить факт исполнения, калибровать всех.

### 7.1 · 4.A — Decision Core (Go/No-Go → Bid)
**Go/No-Go** (рано, по сигналу DFE, до расчёта): профиль компании; квалификация (обороты, референсы, лицензии — частый стоп №1); финансирование (bid/performance bond, кассовый разрыв); **репутация заказчика** (платит ли, как принимает, история «нарисованных» тендеров — из EL); признак «заранее назначенного победителя» (BOQ/квалификация описывают одного).

**Bid/No-Bid/Conditional** (после матчинга, на цифрах): покрытие BOQ в деньгах (🟢+🟡 < ~85% → участие = лотерея); маржа при конкурентной цене; концентрация риска; зависимость от единственного вендора по критической позиции; загрузка своих ресурсов в окно исполнения.

Выход (INV-07) — управленческое решение:
> **Conditional Bid:** подтверждено 91% стоимости BOQ, ожидаемая маржа 14–16%. До пятницы — зафиксировать цену арматуры (LOI с привязкой к исходу тендера) и найти резервного владельца двух кранов. Иначе — No-Bid.

**INV-20 (lock-in):** при решении Bid система **автоматически генерирует** LOI/предзаказ с привязкой к исходу тендера по критическим позициям. Без юридического лока расчётная маржа — галлюцинация. «Наличие сегодня» ≠ «наличие в день подписания».

**P316:** решение выдаётся с тремя вероятностями, TCO-обоснованием, условиями и дедлайном; Conditional без выполненных условий к дате авто-переходит в No-Bid.

### 7.2 · 4.B — Post-submission tracking
После подачи — тот же конвейер продолжает следить: addendum'ы к документации, сдвиги дедлайнов, ответы на вопросы участников (в них меняются объёмы), результаты.

**P317:** addendum к отслеживаемому тендеру распознан, затронутые строки BOQ помечены как требующие пересчёта.

### 7.3 · 4.C — Execution Ledger (факт)
Салфеточный вход со стройки (INV-18): фото акта, голосовое «сегодня простояли полдня, кран не приехал», скан накладной. Атомы: `проект → позиция → план vs факт → причина отклонения → виновник → дата`.
Слои: фактическая себестоимость vs сметная; фактическое поведение вендоров под нагрузкой (→ 3.B); фактическое поведение заказчика (→ Go/No-Go); форма кэш-кривой по типу проекта; где реально умерла маржа (preliminaries, простои, переделки, последняя миля).

**P318:** закрытый проект даёт: дельту план/факт по строкам, обновление репутации задействованных вендоров, обновление профиля заказчика, вклад в исторический буфер накладных.

### 7.4 · 4.D — Calibration loop (замыкание)
Каждый публичный исход и каждый закрытый проект → калибровка:
- цена победителя vs своя оценка рыночной себестоимости → где база SCG врёт (дыра в вендорах / демпинг / «нарисованный» тендер — разные выводы);
- **разбор проигрышей** (самый информативный артефакт): проиграли дешёвому доступу конкурента → искать этого вендора; демпингу → в репутацию + смотреть, как исполнит; «рисунку» → ужесточить Go/No-Go по заказчику;
- перекалибровка весов сигналов DFE и TTL по конкретным заказчикам (у министерства A от распоряжения до тендера 4–6 мес, у госкомпании B от ТЭО до закупки 12–18 мес).

**P319:** после N закрытых циклов горизонты DFE и себестоимости SCG по конкретному заказчику статистически точнее, чем на старте; исторический буфер накладных из 4.C автоматически накладывается на каждую новую смету 4.A.

## 8. Сквозная схема данных (общая для DFE/SCG/EL)

Все три подсистемы и MDC пишут в одну шину фактов. Минимальный общий контур сущностей:

- **Object** — заказчик / регион / тип проекта (якорь для сигналов и прогнозов).
- **Signal** — ранний сигнал спроса (DFE). `{object_ref, тип, вес, source_ref, observed_at, ttl}`.
- **Forecast** — карточка прогноза (DFE). `{object_ref, предмет, бюджет_оценка, окно, p_выйдет, p_в_окно, p_привлекательность, цепочка_улик[]}`.
- **Tender** — опубликованный тендер (DFE). Связан с Forecast (для калибровки).
- **BOQLine** — строка BOQ (DFE/2.A). `{tender_ref, раздел, code, description, unit, qty, spec, тип}`.
- **Vendor** — поставщик/бригада/владелец техники (SCG).
- **CapabilityFact** — атом возможности (SCG). `{vendor_ref, слой, номенклатура, qty, цена, валюта, локация, окно, executable_status, source_ref, observed_at, ttl, confidence}`.
- **ReputationFact** — исход поведения (SCG/EL). `{vendor_ref | object_ref, тип_события, проект_ref, source_ref, observed_at, ttl}`.
- **Match** — сопоставление BOQLine ↔ CapabilityFact (MDC). `{boqline_ref, capfact_ref, светофор, tco}`.
- **Decision** — Go/No-Go, Bid/No-Bid/Conditional (MDC). `{tender_ref, тип, условия[], дедлайн, обоснование}`.
- **ExecutionFact** — план/факт (EL). `{проект_ref, boqline_ref, план, факт, причина, виновник_ref, observed_at}`.

Каждая запись подчиняется INV-15 и INV-16: `source_ref` обязателен, raw-исходник адресуем.

## 9. Ворота приёмки по фазам

- **Ворота Phase 1:** весь egress через валидатор (INV-10); каждый сбой → exception queue, не `null`; возобновляемость (INV-03); regression `P001/P002/P006/P007 + P301–P307` зелёный на живом портале.
- **Ворота Phase 2:** BOQ раскрыт до атомарных строк с типами и spec (P308); forecast калиброван на ретро-выборке ≥30 тендеров (P310); карточка+доставка работают на пороге (P311).
- **Ворота Phase 3:** салфеточный ingestion предложения (P312); репутация как коэффициент доверия (INV-19, P313); Executable Availability (P314); перевёрнутый матчинг «сначала исполнимость» (P315).
- **Ворота Phase 4:** Decision Core выдаёт Conditional Bid с авто-лок-ином (INV-20, P316); post-submission tracking (P317); EL со стройки (P318); calibration loop замыкает петлю и разбирает проигрыши (P319).

## 10. Что НЕ делать (антипаттерны, накопленные из логики системы)

- Не считать «наличие есть → любая цена ок». Наличие даёт право диктовать заказчику, а не соглашаться на любые условия вендора (INV-19 + TCO).
- Не присваивать 🟢 по двум свежим ценам от незнакомцев — нужна история исполнения.
- Не завершать жизненный цикл на подаче — addendum'ы и результаты часть конвейера (4.B/4.D).
- Не хардкодить структуру внешнего источника — только empirical contract + drift (INT-02).
- Не заставлять поставщиков информации заполнять формы — порог входа ноль (INV-18).
- Не выдавать «рекомендую участвовать» — только решение с условиями и дедлайном (INV-07).
