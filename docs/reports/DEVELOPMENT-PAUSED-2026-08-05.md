## 1. Суть конфликта

**Что уже зафиксировано в исходных документах (до сегодняшнего дня, "не подлежит обсуждению"):**

`docs/CONTEXT.md`, раздел "Locked decisions (not up for debate, PRD §13.1 D-ARCH/D-AUTH/D-DATA/D-P0)":
> Stack: React/TypeScript + Python/FastAPI + separate Python worker + PostgreSQL. **Modular monolith.**
> Separate repo/runtime at `C:\Users\orkha\Documents\UNIWatch-v2` (`NFR-ARC-01..06`).

`docs/adr/0001-modular-monolith-boundaries.md`:
> v2 must be a **single deployable unit** for now (**no premature microservices** — no infra budget
> decision has been made, `TBD-05`), but with domain seams strict enough to split out a service later
> without a rewrite.

То есть текущая архитектура — **один процесс, один репозиторий**, `packages/tender`/`packages/vendor`/
`packages/decision`/`packages/algorithm`/`packages/platform` — это просто Python-пакеты внутри одного
FastAPI-приложения (`apps/api`) и одного воркера (`apps/worker`). Границы между `tender` и `vendor`
соблюдаются только на уровне дисциплины импортов внутри процесса (`tender` не читает внутренние таблицы
`vendor` напрямую — только через application contract), но физически это **не два отдельных сервиса**,
а один и тот же деплой.

**Что только что вспомнил и сообщил владелец (2026-08-05, устно, нигде ранее не зафиксировано):**

> Жёсткое требование заказчика: модули **Тендер** и **Вендор** должны работать как **полностью
> отдельные инструменты со своими процессами/деплоем**, общающиеся между собой **через API**
> (не разделяемая БД/общий процесс, а реальный сетевой API-контракт между двумя независимо
> развёртываемыми сервисами).

Это требование **прямо противоречит** ADR-0001 и разделу "Locked decisions" в `docs/CONTEXT.md`.
Подтверждено в разговоре с владельцем (2026-08-05):
- Требование нигде не было записано раньше — не в PRD, не в master-plan, не в
  `TENDER_INTELLIGENCE_SPEC.md`. Это пропуск, который только сейчас всплыл.
- Имеется в виду именно **вариант "полностью отдельные сервисы"** (свои процессы, свой деплой,
  реальный HTTP/API между ними) — не просто более строгая внутрипроцессная API-граница внутри одного
  деплоя.

## 2. Почему это блокирует, а не просто "доделаем потом"

Per `AGENTS.md` (правила репозитория, обязательны для любого агента/человека, работающего с кодом):

- **§2, hard ban:** "Never invent numbers/facts for anything not sourced." Устное новое требование без
  фиксации в исходных документах (`Uniwatch VER2/UNIWatch-v2-PRD-v1.0.md` и т.д.) не может просто
  молча заменить уже зафиксированное решение — по правилу приоритета источников (`AGENTS.md` §1), если
  исходные документы и реальность расходятся, **сначала правятся исходные документы**, а уже потом код.
- **§4, phase discipline:** "Every deviation from PRD/master-plan, or new assumption, is recorded in
  `docs/decisions/OPEN-QUESTIONS.md` — never decided silently." Это расхождение ещё не записано туда
  формально (см. раздел 5 ниже — что нужно сделать перед продолжением).
- Переход "modular monolith" → "полностью отдельные сервисы" — это **не мелкая правка**, а смена
  фундаментальной архитектуры: отдельные процессы/деплои означают отдельные CI/CD-пайплайны, возможно
  отдельные схемы/базы данных, сетевую аутентификацию сервис-к-сервису, service discovery, и
  **инфраструктурный бюджет**, который прямо сейчас **не решён** (`TBD-05` в ADR-0001 — "no infra budget
  decision has been made").
- Часть уже написанного кода (`packages/tender`, `packages/vendor`, `packages/contracts`,
  `apps/api`) была построена в предположении одного процесса/одного деплоя. Если требование
  подтвердится в этом виде, потребуется пересмотр:
  - `apps/api` — сейчас одно FastAPI-приложение; при полном разделении это должны быть **минимум два**
    отдельных сервиса (свой процесс, свой порт/деплой) для `tender` и `vendor`.
  - `packages/contracts` — сейчас "shared OpenAPI/DTO/schema contracts, the only sanctioned
    cross-package data path" **внутри одного процесса**. При реальном разделении это должно стать
    настоящим сетевым контрактом между двумя независимыми сервисами (версионирование API,
    обратная совместимость, сетевые таймауты/ретраи — то, чего сейчас нет, потому что всё было
    in-process).
  - Миграции/схема БД (`migrations/`) — сейчас одна база на весь монолит; при разделении сервисов
    встаёт вопрос: одна общая БД с раздельным доступом по сервисам, или у каждого сервиса своя схема/база.
  - `packages/vendor` пока пустой (только синтетика, ещё не начат предметно) — по счастью, здесь меньше
    уже вложенного труда, который пришлось бы переделывать.
  - `packages/tender` — здесь уже много реального кода (Phase 0/1/2, включая только что смерджённый
    task 2.C) — но `tender` не пересекается с `vendor` физически, только по паттерну (общий
    `packages/platform`), так что риск переделки в `tender` ниже, чем в точке стыка `tender`↔`vendor`
    (которая пока даже не начиналась — `vendor` не дошёл до Bid/No-Bid логики).

## 3. Что уже реально построено и смерджено в `master` (безопасно, не выбрасывается)

Актуально на коммит `6612fc8` (2026-08-05, ветка `master`, синхронизирована с `origin/master`):

- **Phase 0/1 (фундамент):** `packages/platform/` — db, migrations_runner, RBAC (deny-by-default),
  audit (disable-not-delete), correlation, errors (единый envelope), jobs (durable worker jobs с
  `SKIP LOCKED`), outbox (transactional), idempotency, pagination, concurrency (If-Match), egress/
  (SSRF-защищённый исходящий HTTP — validator → registry → DNS resolve → pinned connect),
  exception_queue, proxy (verified peer IP из X-Forwarded-For).
- **Phase 1 (tender ingestion core):** eTender "empirical contract" коннектор — `raw_snapshot.py`
  (сырые данные сохраняются безусловно первыми), `schema_drift.py` (дрейф формата не проглатывается
  молча), `normalized.py`, `bom_lines_job.py`/`boq_completeness.py` (постраничная реконсиляция BOQ,
  `complete` только после доказанного совпадения page/row totals).
- **Phase 2 (BOQ depth + Forecast layer, `TENDER_INTELLIGENCE_SPEC.md` §5):**
  - **2.A** — полная строка BOQ (раздел/code/unit/qty/spec, типы preliminaries/provisional/prime-cost).
  - **2.B** — ingestion сигналов из **трёх** реальных источников: World Bank donor pipeline,
    eTender design/TEO-тендеры, eTender годовые планы закупок. **Реальное пересечение сигналов двух
    независимых категорий доказано** на примере Заqатала (`design_tender` + `procurement_plan`).
  - **2.C** — object identity (канонизация региона из реальных имён покупателей), composite-trigger
    intersection detection (`packages/tender/object_intersection.py`,
    `signals_store.detect_object_region_intersection()`) — **только что смерджено** (PR #1, PR #2).
    Weak/medium/strong confidence-tiers и TTL-decay **сознательно не реализованы** — упираются в
    `TBD-TIS-01`/`TBD-TIS-02` (см. `docs/decisions/OPEN-QUESTIONS.md`, 2026-08-05).
- **CI/GitHub-инфраструктура (сегодня же):**
  - Branch protection на `master` включена и подтверждена реально работающей: обязательные статус-чеки
    **Fast gate** + **Full gate**, запрет force-push и удаления ветки, правило действует и для админов.
  - Обнаружено и исправлено: `etender.gov.az` блокирует TCP-подключения с IP-диапазонов GitHub Actions
    (подтверждено диагностикой — DNS резолвится, контрольный запрос к другому хосту проходит, но и
    `curl`, и «сырой» TCP-коннект к уже резолвленному IP таймаутятся на этапе connect). Live-network
    тесты (`@pytest.mark.live_network`) вынесены в отдельный необязательный CI-job (`live-fetch`),
    Full gate их больше не блокирует.
  - Репозиторий `WISEION/uniwatch-v2` на GitHub; рабочая учётка `accessunico` имеет только Write
    (не Admin/Maintain) — настройки branch protection применялись владельцем вручную через веб-интерфейс.

Всё перечисленное — рабочий, протестированный, смерджённый код. **Ничего из этого не откатывается**
этим документом — вопрос только в том, что строить **дальше**, пока не решён архитектурный конфликт.

## 7. Разрешение (2026-08-05, позже в тот же день)

Пункты раздела 5 пройдены:

1. **Сверка с реальным PRD:** проверено — исходный PRD v1.1 §2.2 явно говорит **обратное** ("не строить
   микросервисы на старте", модульный монолит как не-гол). ADR-0001 был выведен из PRD корректно,
   расхождения не было. Владелец подтвердил: это **новое** требование заказчика, полученное **после**
   утверждения PRD v1.1, нигде ранее не зафиксированное — сам PRD устарел на этом пункте.
2. **PRD исправлен** (по просьбе владельца, мной): `Uniwatch VER2\0_UNIWatch-v2-PRD-v1.0.md` — три
   точечные правки с пометкой "Правка 2026-08-05" (заголовок, §2.2 не-гол, D-ARCH §13.1), остальной
   текст не тронут.
3. **Записано в репозитории:**
   - `docs/decisions/OPEN-QUESTIONS.md`, запись "2026-08-05 — Tender/Vendor must be separate deployable
     services" — полная история обнаружения и решения.
   - **ADR-0006** (`docs/adr/0006-tender-vendor-service-separation.md`) — новое архитектурное решение.
   - ADR-0001 помечен как **частично** superseded (только для пары `tender`↔`vendor`; `decision`/
     `algorithm`/`platform` не затронуты).
   - `docs/CONTEXT.md`, раздел "Locked decisions" — обновлён.

**Принятое решение (масштаб — не самый тяжёлый вариант, осознанно):**
- `apps/api` разделяется на **`apps/api-tender`** и **`apps/api-vendor`** — два независимых
  FastAPI-процесса, каждый свой процесс/порт/деплой.
- `packages/contracts` для этой пары становится настоящим версионируемым сетевым API-контрактом
  (OpenAPI), а не общими Pydantic-моделями внутри процесса — вызовы между `tender` и `vendor` идут
  только через реальный HTTP, никогда не in-process функцией.
- `packages/platform` остаётся общей библиотекой, используемой обоими сервисами — не разделяется.
- **Сознательно НЕ решено сейчас** (реальный инфраструктурный вопрос, привязан к уже открытым
  `TBD-05`/`D-HOST`): отдельная БД/схема на сервис или общий Postgres с разграничением на уровне
  приложения; отдельные CI/CD-пайплайны; отдельные git-репозитории (не выбрано — остаёмся в одном
  репо, раз "свой процесс/деплой" этого не требует).
- `apps/worker` пока не разделяется — это тендер-ориентированный процесс сегодня (`vendor` ещё пустой),
  вопрос откладывается до реального старта работы над вендорами.

**Следующий шаг — это уже не документы, а код:** разбить `apps/api` на `apps/api-tender`/
`apps/api-vendor` и продвинуть `packages/contracts` до реального сетевого контракта. Это отдельная,
достаточно крупная инженерная задача — по правилам этого репозитория (`writing-plans` skill) для неё
нужен свой план перед тем, как трогать код, а не делать это в рамках текущей сессии по ходу дела.

**Итог:** архитектурный конфликт закрыт, разработка может возобновляться. Первая задача при
возобновлении — не новая фича, а сам сплит `apps/api`.
